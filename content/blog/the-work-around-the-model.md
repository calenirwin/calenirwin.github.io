An AI demo can make a task look effortless. Put a question in, wait a moment, and get an answer that would have taken much longer to write by hand. It is easy to imagine the next step: give everyone access and let the time savings add up.

The question I want to spend more time on is what happens around that exchange. Who decides which question to ask? Where does the context come from? Who checks the answer? And what happens when it is wrong?

Those questions are less dramatic than a model producing a page of text. They are also where I would start when deciding whether a tool belongs in a real workflow.

## Start with the work

Before choosing a model, I would try to describe the task in ordinary language. Someone needs to understand a document, prepare a first draft, find a detail, or make a decision. Those are different activities, even if all of them can begin with a chat box.

A useful starting question is: what would a better day look like for the person doing this work?

It might mean finding the right reference without opening ten files. It might mean getting a rough draft early enough to spend more time editing. It might mean recognising that a question needs another person's judgement before any answer is written.

That gives an AI experiment something concrete to aim at. The goal becomes a change in the work, rather than an impressive response in isolation.

## Make the checking visible

I find it helpful to separate producing an answer from deciding whether to use it. A fluent explanation can make those feel like the same step. They are not.

For a low-stakes draft, checking might be a quick read and an edit. For a claim that someone will act on, it might mean opening the source and tracing the answer back to it. The right amount of checking depends on the consequence of a mistake.

I would want that checking step to be part of the design from the beginning. If a tool saves time writing but makes its answer difficult to verify, the work may simply have moved somewhere less visible.

## Leave room for uncertainty

A useful tool should have a way to say that it cannot answer from the information available. It should also leave the person using it with a clear next step: find another source, ask someone, narrow the question, or stop.

That is a different ambition from making every response sound complete. I am more interested in a tool that helps someone move forward with a clear understanding of its limits.

## An experiment worth trying

For a first experiment, I would choose one recurring task and write down what the existing process looks like. Then I would try the AI-assisted version on a small set of examples, keeping the review step intact.

The questions would be practical. Was the result useful? How much editing did it need? Was it easier to check? Did the person doing the task want to use it again?

There is plenty to learn from an answer that is only partly useful. It can reveal missing context, an unclear handoff, or a task that needs a different approach. That learning seems like a better foundation for adoption than assuming that access alone will change how people work.

The model matters. So do the questions, sources, checks, and decisions around it. That surrounding work is what I want to keep exploring here.
